# HOLDOUT policy

**This directory is empty on purpose. The holdout has not been generated yet.**

## What the holdout is for

One question: does the frozen engine generalise, or does it fit the corpus it
was developed against? Every other corpus in this benchmark can answer "how
does it behave"; only this one can answer "is that behaviour real".

## Rules

1. **The holdout is never used for rule development, threshold tuning, or any
   engine modification.** EdgeGuard Core is frozen at
   `f664be6af727a5a1fa8f66e9e2ad07c109263acb`. If the engine changes, every
   prior holdout result is void — not "stale", void — because the holdout's
   only value is that the engine has never seen it.

2. **The holdout is generated by a separate generator, with a separate seed,
   from separate source material.** It does not share a generator with
   `corpus/dev/synthetic_facts`. Sharing one would mean the holdout tests the
   same case families with different numbers, which is not generalisation.

3. **One run.** Each execution against the holdout is appended to
   `holdout.lock` with the engine file hashes, the corpus hash, and a UTC
   timestamp. The lock file cannot prevent a second run; it makes a second run
   visible. Statistical validity decays with each look, and a reader of the
   results is entitled to know how many looks there were.

4. **Not read by default.** The runner requires an explicit
   `--include-holdout` flag. Absent that flag, the loader does not open this
   directory at all.

5. **No development corpus case may appear here, in any lightly reworded
   form.** Enforced mechanically before any holdout run: exact normalised-text
   equality and shingle-overlap similarity against the entire development
   corpus. Any hit fails the run rather than dropping the case, because a
   near-duplicate that slipped in means the generator is drawing on
   development material and the whole set is suspect.

## Known contamination in this repository

These files predate the benchmark and were used for rule development and
threshold calibration. Nothing in them, and no paraphrase of anything in them,
may be used to build the holdout:

- `redteam_adaptive.py` — 59 cases, with a regression gate pinned to values
  measured against those same cases.
- `corpus_enterprise.py` — enterprise tool-invocation and behaviour-hijack
  corpus, merged by `residual_gap_protocol.py`.
- `measure_grey_rate.py` — prices `control-plane/candidate-flag-rules.yaml`
  against benign and attack traffic.
- `hardcore_redteam.py`, `comprehensive_test.py`, `enterprise_audit.py`.
- The Tier-1 regression fixtures in `tests/`.

They are development data by definition. They may be used in
`corpus/dev/`, clearly labelled, but a result measured on them is a training
score and must never be reported as a generalisation score.
